Closing the loop on “Your kind of trip”

A co-traveller shares their travel style and the app says nothing back. Two-phase fix: acknowledge and route to value now, feed styles into route generation next.

2026-08-10 Branch: collab-tier2 Observed on the Ziro trip, user "tripman"

What happened

The second traveller on the Ziro trip opened Your kind of trip, wrote a real, useful style — “I want to spend at least 5–6 days in the festival and also some quiet villages” — and saved. Every backend step worked. Nothing visible changed.

✓ Style saved to trip_preferences verified on staging, 12:40 UTC
✓ Style attached to every chat request client → preferences[]
✓ Trippy's prompt gains a per-traveller block chat fn, dynamicContext
✗ User sees any of this sheet closes, routes unchanged

This is working as designed — the design just stops one step short. The Phase 5 plan scoped v1 to chat-only:

“D-P2 — Does IG use prefs too? Feed prefs into itinerary generation for shared trips (higher value, more work), or chat-only for v1 [recommend chat-only first, IG as fast-follow].” phase5-6-plan.md

The value exists but is latent — it only surfaces if the traveller happens to chat with Trippy afterwards. Saving a form and receiving silence reads as a bug even when it isn't one. Both phases below attack that gap; neither changes the save-is-a-plain-DB-write architecture.

Phase A · ship now

Acknowledge, then route to the value

The style already changes what Trippy will say — so the cheapest honest fix is to tell the traveller that, and put the payoff one tap away. Two touchpoints, both purely frontend, no new LLM spend until the user opts in by tapping.

Phase B · fast-follow

Styles reach the route generator

Phase A makes the existing value visible. Phase B is the value the traveller actually expected: the plans themselves respond. This is the D-P2 fast-follow the plan already anticipated — thread preferences[] into RG and IG for shared trips, and nudge a regeneration when a new style lands after plans exist.

Item Spec
RG request generate-brainstorm body gains preferences: [{name, prefs_text}] (shared trips only). Prompt: per-traveller block + rule “each route's points must address each named traveller's stated needs” — same shape as the existing traveller-notes rule.
IG request Same block into generate-itinerary; day text may attribute (“quiet Siiro morning — Achin's pace”).
Nudge trigger Realtime trip_preferences insert/update where tier-1 routes exist and author ≠ viewer, or on next trip open. One live nudge at a time; dismiss persists per (trip, style version).
Cost One RG run per accepted nudge — normal pooled-credit charge, ~6 credits. Declining costs nothing.
Prompt caching Prefs go in the user message (uncached), never the cached system prefix — mirrors how chat does it.
Effort ~2 days: prompt work + nudge UI + regenerate threading + E2E.

Guard-rails, both phases

No surprise spend. Every LLM call stays behind an explicit tap. The failed alternative — Trippy proactively posting in the group chat on every save — was considered and dropped: it charges the pool for a message nobody asked for, and three travellers editing styles in one evening would make Trippy spam the thread.

Idempotent nudging. Chip and nudge key on (trip_id, user_id, updated_at) of the style row — re-saving the same text doesn't re-arm them.

Solo trips stay byte-identical. Everything here gates on isSharedTrip, consistent with the rest of the collab stack.

Decisions needed
1. Ship Phase A on collab-tier2 now? (frontend-only, no migration)
2. Phase B nudge default: propose batched — one nudge per trip-open summarising all new styles, not one per save.
3. Phase B copy: “Rework the plans” vs “Rebalance” — mock uses Rework; “rebalance” reads more technical.
